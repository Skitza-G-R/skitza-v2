## 3. The finding that changes the estimate

The issue estimates M–L, one to two weeks. **A large part already exists.**

`applyTemplate` in `apps/web/src/components/dashboard/active-work-import/model.ts` already
copies, from a Store product, exactly what SK-299 wants defaulted: tax mode, tax rate, currency,
included song spaces, payment plan and monthly count, deliverables, rights, agreement text and
royalty terms. `StoreTemplateOption` is the shape it reads, and the workspace already passes a
`templates` list down to the editors.

So the work is a thin quick-row shell over machinery that is already there, plus the four gaps
below. Re-estimate once you have read the code; do not just repeat "one to two weeks".

### The four real gaps

1. **Reverse tax maths does not exist.** `applyTemplate` copies the product's *subtotal*.
   SK-299 wants the producer to type the *total* and have subtotal and tax derived backwards
   from it. `apps/web/src/lib/tax-mode.ts` has `applyTaxToCents` and `taxTotalMultiplier` but no
   inverse. Write one, with tests for all three modes (`tax_free`, `tax_included`, `tax_added`)
   and for rounding at the edges. Off-by-one here becomes wrong money in a frozen snapshot.
2. **The quick-row UI.** Five fields instead of the three-step editor
   (Client/Project → Agreement → Payment). "Change details" must open the existing full editor
   prefilled, and nothing may be saved before the producer confirms the summary line.
3. **"Paid so far" allocation.** A payment belongs to exactly one installment. Allocate to the
   first installment only when the amount fits; otherwise the row goes to Needs info with
   "Payment must be assigned to one installment" and the producer splits it in the full editor.
4. **The post-import first paint and WhatsApp message**, only if Gili picks the whole issue.

## 5. Rules that must not break

From the issue, PRD §8.7 and SK-255. Breaking any of these is worse than shipping late.

- The frozen snapshot must be complete and exact: subtotal, tax mode, rate, amount, total,
  currency, included song spaces, plan, schedule. **Defaults are proposals; nothing is saved
  until the producer confirms.**
- Provenance stays `imported_existing_work` with a producer attestation, never an artist
  acceptance.
- **Silent creation.** No email, WhatsApp, reminder or artist notification on save. Copy link and
  WhatsApp never mark a client Invited; Invited means the email provider accepted a send.
- Idempotent per row with a stable operation key. Retries never duplicate rows, and partial batch
  success is preserved.
- Every query scoped by `ctx.producerId`. Product and template ownership verified server-side.
  **Never trust totals, tax, currency or plan from the UI.**
- Session allowance terms are immutable in the database (a trigger from migration `0038`), and
  purchases cannot be hard-deleted. Get the maths right the first time.

## 6. This one writes real data — set up a sandbox first

SK-298 wrote nothing, so it was safe to test locally. **SK-299 creates clients, projects,
purchases, installments and payments.**

`apps/web/.env.local` on this Mac points `DATABASE_URL` at the **live production database** while
using Clerk **test** keys. Dev login plus real customer data is the trap. Never run a write-path
test against it.

Use the proven sandbox recipe instead: `CREATE DATABASE sk299_sandbox` on the same Neon endpoint
(`neondb_owner` can create databases, no Neon MCP or branch needed), restore with
`pg_dump --schema-only`, point `DATABASE_URL` at it, and `DROP DATABASE` at the end. Details are
in the assistant's memory under the local write-test recipe.

Never run `pnpm -F db db:migrate` or `drizzle-kit migrate`. Use `$skitza-migrate`.

## 7. Workflow facts worth knowing

- Base branch is `v3-clean`. Never commit to `main`. Direct pushes to `v3-clean` are blocked;
  open a pull request.
- Use Linear's exact generated branch name:
  `giasraf/sk-299-bring-in-active-work-quick-row-with-defaults-from-the-first`.
  Move the issue to In Progress.
- Verification gate before any claim of "done": from `apps/web` run `pnpm typecheck`,
  `pnpm lint`, `pnpm test`, then `pnpm typecheck` in `packages/db`. Lint runs with
  `--max-warnings 0` on Vercel.
- **A known CI flake:** the `test` workflow's "Build web and admin" step sometimes fails with
  `NextFontError: Failed to fetch 'Outfit' from Google Fonts` and `ETIMEDOUT`. It is unrelated to
  app code. Re-run the job.
- **Re-merging a branch after its squash merge conflicts**, because the merge base predates the
  squash. Fix with `git reset --hard origin/v3-clean`, cherry-pick the new commit, then
  `git push --force-with-lease`.
- Promote recipe, only with Gili's explicit approval for that exact deployment:
  `npx vercel redeploy <preview-url> --target production` from the repo root. It takes about six
  minutes and aliases skitza.app automatically. There is no `--yes` flag on `redeploy`.
- A Vercel preview link Gili can open on his phone:
  the Vercel MCP's `get_access_to_vercel_url` returns a URL with a share token that skips the
  Vercel login. It lasts 23 hours.

## 8. Two lessons from SK-298 worth carrying over

- **jsdom cannot see layering or layout.** All 7,885 tests passed while a confirmation dialog sat
  unreachable underneath an overlay, and while a control spilled past a frame. Anything visual or
  stacked must be checked in a real browser. The repo has no Playwright: `npm i playwright-core`
  in the scratchpad and launch with `chromium.launch({ channel: "chrome" })`.
- **The Browser pane throttles timers when hidden.** Anything time-based looks broken there while
  working fine under headless Playwright. Verify timing with Playwright, not the pane.
